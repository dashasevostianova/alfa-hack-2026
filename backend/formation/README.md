# Модуль формирования и рассмотрения заявки

Python-модуль подключён к существующему React-фронтенду: анкета → подбор кредита → формирование → список заявок с этапами рассмотрения → сохранённый результат. SQL-схема и Java-бэкенд не изменены.

## Запуск

Из корня репозитория, при работающей PostgreSQL:

```bash
python3 -m venv backend/formation/.venv
backend/formation/.venv/bin/pip install -r backend/formation/requirements.txt
backend/formation/.venv/bin/python backend/formation/server.py --seed-products
```

Если системный Python уже содержит `psycopg2`, достаточно `python3 backend/formation/server.py --seed-products`.

В другом терминале:

```bash
cd frontend
npm install
npm run dev
```

Открыть адрес, который напечатал Vite, обычно `http://127.0.0.1:5173`. Если порт занят: `npm run dev -- --port 5174`, затем открыть именно `http://127.0.0.1:5174`.

Модуль теперь включён по умолчанию при браузерной демо-авторизации. Старый запуск `npm run dev -- --mode formation` также работает. Для возврата к прежним браузерным заявкам установить `VITE_FORMATION_DEMO=false`. Если `VITE_USE_MOCKS=false`, сохраняется подключение основного Java API (кроме случая явного `VITE_FORMATION_DEMO=true`).

После изменения Python-кода перезапустить Python-сервер. Изменения React подхватываются Vite автоматически. Для production-сборки: `npm run build`; для её размещения нужен прокси `/api/formation` на Python. Vite проксирует этот путь в dev на `127.0.0.1:8081`.

Настройки БД читаются из `Docker/.env`; переменные окружения имеют приоритет: `DB_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`. `--seed-products` добавляет два демонстрационных продукта только в пустой каталог; существующие продукты не меняет. Требуется схема `Docker/init/01_schema.sql`. Модуль не выполняет миграций и не удаляет существующие данные.

## Анкета: автоматически или вручную

После ввода полного ИНН через 400 мс выполняется поиск. Результат устаревшего запроса при смене ИНН игнорируется.

- ИНН есть в CSV: автоматически заполняются пустые поля ОКВЭД (сфера деятельности) и средней месячной выручки (годовая / 12). Вручную изменённые значения не перезаписываются. Реквизиты компании и финансовые показатели для заявки берутся из CSV; название компании — из анкеты. Ручное значение месячной выручки в анкете не заменяет годовую отчётность из CSV.
- ИНН отсутствует в CSV: появляется раздел ручного ввода. Обязательны юридическая форма, дата регистрации, ОКВЭД, статус компании и чистая прибыль за год (включая нулевую или отрицательную). ОГРН/ОГРНИП, текущие обязательства, возможная просрочка, капитал и активы необязательны. Годовая выручка рассчитывается как месячная × 12.
- Пустые необязательные показатели сохраняются как неизвестные, без фиктивных нулей. Все суммы ручного ввода — в рублях.
- Ошибка чтения/проверки источника не считается отсутствием компании: интерфейс показывает ошибку и повтор проверки. Неподдерживаемая форма или повреждённый CSV требуют исправления исходных данных.

Примеры из CSV: `4217064462` и `4217064470`. Для первого ожидаются: выручка **3 222 000 ₽**, прибыль **−482 000 ₽**, синтетическая оценка возможной текущей просрочки **3 165 ₽**, долг **нет данных**, капитал **3 862 000 ₽**, активы **4 495 000 ₽**.

CSV хранится только на бэкенде: `backend/formation/data/companies_small.csv`. Скопирован из предоставленного `companies_small_fixed.csv`, UTF-8 с BOM, разделитель `;`. Можно переопределить путь через `COMPANIES_CSV`. Загружается один раз, индексируется по строковому ИНН; дубли останавливают запуск. ИНН/ОГРН не преобразуются в float. Файл исключён из Git, для передачи коллегам его нужно предоставить отдельно либо заменить синтетическими данными.

## Формирование и сохранённый отчёт

«Оставить заявку» создаёт реальный `DRAFT` с выбранными условиями, компанией и финансовым снимком, затем открывает `/applications/:id/formation`. Новая страница сначала читает состояние заявки через GET:

- Если это DRAFT, запускает формирование и анимацию параллельно. После серверного сохранения и минимум трёх секунд показывает готовый отчёт.
- Если заявка уже сформирована, сразу показывает сохранённый отчёт. POST формирования, анимация этапов и расчёт CSV повторно не запускаются.

Снимок отчёта хранится в существующем текстовом поле `finances.account_statements` как JSON с маркером `formation_snapshot_v1`. Он содержит реквизиты на момент подачи, источник (`csv` или `manual`), показатели (включая капитал/активы) и время завершения формирования. Обычные финансовые показатели одновременно сохраняются в собственных столбцах. Это явный формат данных модуля, а не новая таблица или связь: `finances.application_id → application.reg_id → business.reg_id` остаётся прежней.

Для заявок старой версии с пустым `account_statements` при первом просмотре создаётся снимок из сохранённых финансов и доступных сведений CSV. Уже существующие текстовые выписки не перезаписываются. Если у старой заявки нет снимка, а в кабинете несколько компаний, привязка не угадывается: требуется явно восстановить ИНН старой заявки. Новые отчёты не зависят от последующих изменений CSV. Капитал/активы доступны в JSON-отчёте; отдельных SQL-столбцов для выборок по ним по-прежнему нет.

Формирование переводит DRAFT в SUBMITTED. Это ещё не одобрение. Повторный POST по тому же ID не дублирует финансовые строки и не меняет время формирования. Создание повторного черновика с тем же ИНН и условиями в этой регистрации использует существующий DRAFT. Новая осознанная подача после завершения предыдущей создаёт новую заявку.

## Рассмотрение на существующей странице «Ваши заявки»

Страница опрашивает API каждые три секунды, пока есть незавершённые заявки. С момента завершения формирования идут демонстрационные этапы:

1. 0–5 секунд: «Отправлено» — `SUBMITTED`.
2. 5–10 секунд: «Проверка» — `DOCS_REQUESTED`.
3. 10–15 секунд: «Рассмотрение заявки» — `IN_CHECK`.
4. После 15 секунд: «Рассмотрено», результат сохраняется в `decision`, статус — `APPROVED` или `REJECTED`.

Переходы выполняются сервером при GET заявки/списка и сохраняются в БД. Отдельного фонового планировщика нет: после отсутствия на странице следующий запрос догоняет актуальный этап. Завершённый результат не пересчитывается при повторном открытии, перезапуске Python или обновлении страницы.

Правила повторяют существующий `demoDecision` во фронтенде: до 2 млн — демонстрационное одобрение; до 5 млн — предложение уменьшить сумму и подать заново; свыше — демонстрационный отказ. Это имитация рассмотрения, не кредитный скоринг и не банковское решение. Структура результата (summary, reasons, recommendations) хранится JSON-текстом в существующем `decision.reason`; вид решения — в `decision.decision`. Для предложения доработки используется `REWORK`, интерфейс отображает `REVISION` и кнопку повторной подачи. Основная команда сможет заменить эти правила своим сервисом.

Ссылка «Данные формирования» открывает готовый отчёт. «Продолжить» при одобрении ведёт на существующую `/approved/:id`; этот следующий экран оставлен в исходном виде.

## Ограничения и интеграция

- Авторизация и анкета пока используют существующее браузерное демо-хранилище. Для каждого аккаунта создаётся отдельный случайный bearer-токен. Его хеш идентифицирует локальную регистрацию `reg`. Переданный клиентом `reg_id` не используется. Для production требуется интеграция с серверной авторизацией проекта.
- Python слушает только loopback и не разрешает CORS. Не публиковать наружу без основной авторизации. Очистка localStorage удаляет привязку демо-токена.
- Один кабинет может подавать заявки для нескольких компаний: достаточно изменить ИНН и сведения в анкете. Каждая заявка сохраняет собственный снимок компании, поэтому смена ИНН не меняет старые отчёты. Повторный черновик определяется по ИНН вместе с условиями кредита. Компания чужой регистрации не присваивается и не перезаписывается. Если ИНН уже занят, использовать исходный аккаунт.
- Персональные данные анкеты не сохраняются в `person`: текущая форма не содержит всех обязательных паспортных и регистрационных сведений этой таблицы. Фиктивные значения не создаются.
- Финансовые вычисления из CSV: `Decimal`, перевод тысяч рублей в рубли; долг = `long_term_borrowed_funds * 0.85 + short_term_borrowed_funds * 1.25`; оценка возможной просрочки = `accounts_payable * 0.005`. Округление до рубля HALF_UP. Ограничение денежных INTEGER проверяется до записи. Возможная будущая согласованная миграция — BIGINT/NUMERIC и отдельные столбцы капитала/активов.
- Технические warnings остаются в API, в отчёте не отображаются. ЕГРЮЛ/ФНС имитируются и явно помечены как демонстрационные.

## API

Префикс `/api/formation`, заголовок `Authorization: Bearer <случайный UUID>`.

- `GET /products` — продукты PostgreSQL.
- `GET /companies/{inn}` — `{found:false,inn}` для отсутствующего ИНН; иначе реквизиты, `calculated`, `stored`.
- `POST /draft` — `{profile,productId,amount,months,purpose}`. Дополнительные поля profile для ручного сценария: `manualBusiness:{legalForm,ogrn,registrationDate,okved,status}` и `manualFinances:{netProfit,currentLoans,taxArrears,equity,assets}`. Дата ISO, финансовые поля могут быть строками.
- `POST /applications/{id}/form` с `{}` — завершение формирования существующего черновика.
- `GET /applications/{id}` — сохранённый отчёт и актуальный этап.
- `GET /applications` — список только текущей регистрации с сохранением этапов.

Ответ содержит обычные поля frontend-модели, `company`, `finances`, `calculated`, `source`, `formationStatus` и `warnings`. Decimal сериализуется строкой без потери точности.

## Проверки

```bash
python3 -m unittest discover -s backend/formation -v
FORMATION_TEST_DB=1 python3 -m unittest discover -s backend/formation -v
cd frontend
npm test
npm run build
```

Интеграционная проверка использует SAVEPOINT и общий ROLLBACK. Проверяет оба источника данных, сохранение финансов, повторы, права доступа, восстановление отчёта без CSV, последовательные этапы и неизменность окончательного результата. Тестовые строки не сохраняются; последовательности ID могут продвинуться.
