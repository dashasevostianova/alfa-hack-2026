# Подписание и демонстрационная выдача

Полный сценарий работает в основном приложении **http://127.0.0.1:8088** через Java API и PostgreSQL.
Подписание и выдача учебные: подпись и юридическая подлинность не проверяются, движение денег отсутствует.
Прежний отдельный mock-режим сохранён для разработки.

## Общий запуск

Из корня проекта с работающим Docker Desktop:

```powershell
docker compose up --build -d --wait
```

Откройте http://127.0.0.1:8088. После обновления Java может потребоваться повторный вход:
серверные сессии по-прежнему в памяти, аккаунты, анкеты, заявки и оформление сохраняются в PostgreSQL.
Менять `frontend/.env` или включать `VITE_USE_MOCKS=true` для Docker не требуется.
Не используйте `docker compose down -v`: это удаляет данные БД.

1. Войдите в существующий или зарегистрируйте синтетический аккаунт.
2. Заполните анкету. Подготовка компании через formation и получение ставок через parser работают как прежде.
3. Выберите актуальное предложение, сумму и срок; отправьте заявку.
4. Откройте «Заявки» и дождитесь демонстрационного решения (15 секунд от подачи).
5. «Перейти к подписанию» → «Сформировать договор» → «Скачать договор PDF».
6. Загрузите условно подписанный PDF до 10 МБ; можно использовать скачанный файл.
7. Подтвердите условное подписание и перейдите к выдаче.
8. Нажмите «Запустить симуляцию выдачи». Результат и история сохраняются после обновления и повторного входа.

До 2 000 000 ₽ включительно — одобрение; свыше 2 млн до 5 млн включительно — предложение уменьшить сумму
до 2 млн и подать новую заявку; свыше 5 млн — отказ. Это явно обозначенная демонстрация, не ML-скоринг.
Ставки, выбранные предложения, сведения компании и серверные проверки подачи не подменяются моками.

## Демонстрационное решение

Отдельный `DemoLoanReview` включён в Compose через `LOAN_DEMO_DECISION_ENABLED=true`.
Без этой настройки при отдельном запуске Java новые решения автоматически не создаются.
Чтобы отключить симуляцию, задайте в корневом `.env` `LOAN_DEMO_DECISION_ENABLED=false`
и пересоздайте backend через Compose. Уже сохранённые демо-решения остаются доступны.

Алгоритм выдаёт промежуточные статусы через 5 и 10 секунд, окончательное решение через 15 секунд.
Результат сохраняется один раз в `loan_demo_review` при чтении заявки; точное время — момент фиксации сервером.
Существующие строки `decision` и исходный статус в таблице `application` не перезаписываются.
Если у заявки появляется настоящее серверное решение, оно имеет приоритет над демо.
Будущая ML-модель должна записывать решение через сервер; модуль подписания от её реализации не зависит.

## Страницы и состояния

- `/applications/:id/sign` — условия, договор, загрузка и подтверждение.
- `/applications/:id/issued` — запуск симуляции и сохранённый результат.
- `/approved/:id` — совместимый переход на подписание.

К `LoanApplication` добавлены необязательные `borrowerSnapshot`, `fulfillment`, `decisionSource`, `decisionAt`.
Исходные поля и прежние пользовательские данные совместимы.

```text
без fulfillment → AWAITING_SIGNATURE → DOCUMENT_UPLOADED → SIGNED → ISSUED
                         ↑                    |
                         └── удаление PDF ────┘
```

Каждая операция на сервере проверяет владельца, завершённость рассмотрения, одобрение и предыдущий этап.
Ожидающие, отклонённые и REVISION-заявки недоступны для подписания. Выдача требует подписания.
После подписания документ нельзя заменить/удалить. Повторные confirm/issue возвращают существующий результат.
Блокировка строки `application FOR UPDATE` и транзакции сериализуют действия из разных вкладок/запросов.

Номер, дата, реквизиты и условия договора фиксируются один раз. PDF формирует сервер через Apache PDFBox
с локальным шрифтом DejaVu Sans; повторное скачивание возвращает те же сохранённые байты.
Лицензии шрифта находятся рядом с ним в ресурсах frontend/backend.
Реквизиты берутся из снимка анкеты, сохранённого при подаче. Для старых записей без снимка используется
текущая анкета с явной пометкой. При неизвестной годовой ставке, изменении условий или отличающихся
условиях настоящего одобрения оформление блокируется: `suggestedAmount` не считается одобренной суммой.

История содержит реальную дату подачи и фактические события оформления. Время получения решения
модулем не выдаётся за отсутствующую историческую дату одобрения. Даты хранятся в ISO UTC и
отображаются в часовом поясе браузера.

## Добавочное хранение

Миграция `Docker/init/04_loan_fulfillment.sql` автоматически применяется как к новой, так и к существующей БД:

- `loan_demo_review` — сохранённое демонстрационное решение, один результат на заявку.
- `loan_fulfillment` — JSON-состояние, история, исходный PDF и загруженный PDF в BYTEA, одна строка на заявку.

Исходная схема, enum-статусы, таблицы заявок, решений и финансов не меняются. Для учебного файла до 10 МБ
используется PostgreSQL; отдельное файловое хранилище/том не нужен. Файлы не возвращаются в списках заявок.
Проверяются расширение, MIME (может быть пустым), непустой размер, лимит 10 МБ и заголовок `%PDF-`.
Это базовая проверка формата, не полноценный анализ PDF, проверка подписи или соответствия текста договора.
Для будущего промышленного хранения потребуется отдельное объектное хранилище и его политика доступа.

## Реализованный API

Префикс `/api`, существующая cookie-сессия. Перед изменениями клиент получает `/auth/csrf`.
Владелец определяется из сессии; userId и условия договора клиент не задаёт.

| Метод | Путь после /api | Ответ |
| --- | --- | --- |
| GET | `/applications/{id}/fulfillment` | Заявка с состоянием оформления |
| POST | `/applications/{id}/fulfillment/contract` | Заявка с подготовленным договором |
| GET | `/applications/{id}/fulfillment/contract.pdf` | Сохранённый PDF; фиксирует подготовку к скачиванию один раз |
| POST | `/applications/{id}/fulfillment/document` | Multipart поле `file` → обновлённая заявка |
| DELETE | `/applications/{id}/fulfillment/document` | Обновлённая заявка |
| POST | `/applications/{id}/fulfillment/confirm` | Заявка с `SIGNED` |
| POST | `/applications/{id}/fulfillment/issue` | Заявка с `ISSUED` |

GET `/applications` и `/applications/{id}` дополнены необязательным `fulfillment`.
Чужой/неизвестный ID → 404; неверный переход → 409; неверный формат → 400/415;
слишком большой файл → 413; нет сессии → 401; CSRF → 403.
Лимит nginx повышен только для маршрута загрузки, общий лимит JSON-запросов сохранён.

## Проверки

```powershell
cd frontend
npm.cmd test
npm.cmd run build
cd ..
python scripts/check_loan_fulfillment.py
```

Сквозной Python-тест требует работающего Compose и доступности прежнего источника предложений.
Создаёт только синтетические аккаунты/заявки, оставляет их в локальной БД. Проверяет реальные
HTTP-запросы, три решения, PDF, загрузку более 64 КБ, лимит 10 МБ, CSRF, чужие заявки,
повторные/параллельные операции, сохранность условий и восстановление после входа.

Java-тесты, включая существующие:

```powershell
docker build --target build -t alpha-credit-java-tests backend/hack
docker run --rm alpha-credit-java-tests ./mvnw --batch-mode --no-transfer-progress test "-Dtest=ApplicationServiceTests,ExternalServicesTests,LoanFulfillmentTests"
```

## Прежний mock-режим

Для изолированной разработки задайте `frontend/.env.local`: `VITE_USE_MOCKS=true`, затем
`cd frontend` и `npm run dev`. Адрес http://127.0.0.1:5173, backend не требуется.
Данные остаются в прежней единой базе localStorage; сохраняются только метаданные принятого PDF,
сам файл не хранится. Эти аккаунты/заявки не синхронизируются с PostgreSQL на `:8088`.
