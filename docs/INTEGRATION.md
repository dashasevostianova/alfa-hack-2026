# Контракт интеграции dev-2

Добавочный контракт [подписания и демонстрационной выдачи](LOAN_FULFILLMENT.md)
реализован через Java/PostgreSQL и работает на основном порте 8088. Добавлены две таблицы;
существующие таблицы, API и настоящие решения сохранены. В Compose подключена модель из frontend; прежняя симуляция одобрения по сумме удалена.

Все внешние запросы проходят через Java `/api`. Внутренние formation и parser не публикуют порты. Авторизация — HttpSession; ID владельца берётся из сессии. Перед POST клиент получает GET `/auth/csrf` и посылает заголовок `X-CSRF-TOKEN`. После входа ID сессии и CSRF обновляются.

Фронтенд сохраняет вызов сервиса модели через same-origin `POST /model/predict` и локальное хранение результата из ветки frontend. Сервис принимает строго восемь числовых полей `business_age_years`, `legal_form`, `revenue`, `net_profit`, `current_loans`, `purpose`, `amount`, `term_months` и возвращает `{prediction: 0 | 1}`. Для оформления фронтенд дополнительно вызывает `POST /api/applications/{id}/model-decision` с cookie-сессией и CSRF, без признаков и без клиентского решения. Java сама строит те же восемь признаков из сохранённой заявки, вызывает scoring и транзакционно записывает результат в существующую таблицу decision и статус application. Локальный результат не заменяет уже сохранённое серверное решение. Ошибка модели возвращает 502 и не превращается в демонстрационное одобрение.

| Метод | Путь после /api | Результат |
| --- | --- | --- |
| GET | /auth/csrf | `{headerName,token}` |
| GET | /auth/login-availability?login=... | `{available}` |
| POST | /auth/register | `{login,password}` → `{id,regId,login,profileComplete}` |
| POST | /auth/login | Те же credentials → пользователь и cookie |
| GET | /auth/me | Пользователь либо 401 |
| POST | /auth/logout | 204 |
| GET | /profile | Полная сохранённая анкета либо пустой ответ |
| POST | /profile | Анкета → анкета с серверным `prepared` |
| GET | /formation/companies/{inn} | Поиск через read-only formation; `found:false` только для отсутствующего ИНН |
| GET | /loans/products | Каталог существующего Java ProductService |
| GET | /loans/quote?collateral=false | `{offers,key,businessAgeMonths,businessAgeBucket,legalForm,fetchedAt,source,collateral}` |
| POST | /applications | `{productId,amount,months,purpose,collateral,bankOfferId,annualRate}` → сохранённая заявка |
| GET | /applications | Полные карточки текущего пользователя, новые первыми |
| GET | /applications/{id} | Карточка и снимок формирования; чужой ID → 404 |

Значения `purpose` — русские подписи из `frontend/src/types.ts`; адаптер сопоставляет их существующему Java enum и SQL enum. ID продукта может передаваться строкой или целым числом.

Анкета сохраняет прежние поля `fullName,email,phone,passport,companyName,inn,industry,monthlyRevenue`, дополнительно обязательны `birthDate` (ISO, возраст 18+) и `citizenship`. Для отсутствующего ИНН используются прежние `manualBusiness` и `manualFinances`. Сервер самостоятельно строит `prepared`; присланное клиентом значение не считается достоверным.

`prepared` содержит `company`, `stored` (финансы в рублях) и `report`. Юридическая форма для ставки берётся только отсюда. Месячная выручка ручной анкеты преобразуется в годовую существующей функцией formation; показатели найденного ИНН берутся из CSV.

## Изменения относительно прежнего Java API

URL `/api/applications` сохранён, запись выполняет неизменённый `ApplicationService.submit(ApplicationSubmission)`. Добавлен адаптер: вместо доверия клиентским regId и вложенным person/business/finances он получает владельца из сессии, собирает существующий DTO из сохранённой анкеты и вызывает сервис. Клиент отправляет только выбранные параметры. Старые клиенты, отправляющие полный ApplicationSubmission напрямую, нужно обновить.

Ответ списка теперь содержит данные для UI вместо трёх полей id/regId/status. `/api/profile/{regId}` заменён на `/api/profile`, чтобы не раскрывать чужие анкеты. Вход, проверка текущей сессии, CSRF и выход добавлены, поскольку исходный Java API имел только регистрацию.

## Предложения и ставки

Java вычисляет полные месяцы существования бизнеса из `prepared.company.registration_date` на текущую дату UTC. Клиент не может передать возраст, форму бизнеса или собственный список предложений. Фильтр источника — возраст бизнеса, не срок кредита: для ООО граница 9 месяцев, для ИП — 3. Значение на границе относится к нижней группе.

Java вызывает новый GET `/offers?legal_form=IP&business_age_months=12&collateral=false` парсера. Ответ содержит `businessAgeBucket` и массив `offers`. Форма регистрации выбирается на сайте первой, поскольку от неё меняется порог возраста. Прежний GET `/` парсера сохранён для совместимости, общий кабинет его не использует.

Предложение: `{id,name,ratePercent,rateText,rateUnit,annualRate,detailsUrl}`. ID — стабильный хеш названия. `rateUnit` принимает `annual`, `monthly`, `monthly_overpayment`, `not_published`. Только `annual` содержит числовой `annualRate`; для остальных — null. Месячная переплата «Альфа-Селлер Кредита» не превращается в годовой процент. Карточки извлекаются только из видимого блока калькулятора, отдельные продукты не объединяются в одну ставку.

Кэш предложений — общий для всех пользователей, по восьми сочетаниям возрастной группы/формы/залога, срок — 24 часа с успешного получения каждой группы. Parser прогревает группы в фоне при запуске и проверяет срок каждые 60 секунд; просроченные группы обновляются автоматически, даже без пользователей. Данные сохраняются в Docker-томе `bank_offers_cache` (`/cache/offers.json`), поэтому перезапуск не вызывает повторный парсинг свежих групп. Одновременные запросы одной группы используют одну загрузку. Java сохраняет исходный `fetchedAt` парсера и не продлевает срок ставок при перезапуске. При ошибке источника просроченные ставки не выдаются; повторная попытка — через 5 минут, актуальные группы продолжают работать. Тайм-аут внешнего запроса — 180 секунд. Для ИП ключ может выглядеть как `Более 3 месяцев|Без залога|Для ИП`. Изменение срока кредита с 9 на 10 месяцев не меняет возрастную группу. Параметр `months` для GET quote больше не используется.

При POST заявки обязательны `bankOfferId` и `annualRate`. Сервер повторно получает актуальный список, выбирает предложение по ID и сверяет ставку. Неизвестный/исчезнувший ID либо изменившаяся ставка → 409; продукт без годовой ставки → 422; сохранения заявки нет. Некорректные или недоступные данные источника → 502. Дублирующиеся ID и годовой процент у месячной переплаты отклоняются.

Сумма и срок кредита проверяются существующим Java-сервисом по пределам таблицы `product`. Новый запрос парсера не вводит их во внешний калькулятор: его результат — предварительные тарифные предложения, а не персональная оферта. Для кредитной линии и овердрафта UI показывает условный аннуитетный расчёт, фактический график отличается.

## Хранение

Анкета до подачи: `integration_profile.payload JSONB`, ключ — `reg_id`. Эта добавочная таблица нужна потому, что исходная application требует выбранные продукт, сумму и срок, которых на шаге анкеты ещё нет.

При подаче существующий Java-сервис сохраняет person, business, application и finances. Снимок полной анкеты, залога, списка предложений и выбранного `bankOffer` лежит в существующем поле `finances.account_statements` с kind `integration_snapshot_v1`. Заявка переводится в SUBMITTED. ML-модель подключена отдельным сервисом из ветки frontend; серверное подтверждение сохраняет результат в decision. Таблица loan_demo_review читается только для совместимости с прежними данными; новые демо-решения не создаются. Существующие таблицы и данные не удаляются.

Форма подготовки сохраняет анимацию. Повторный просмотр отчёта вызывает только GET и не создаёт дополнительную заявку.

## Ошибки

Ошибки имеют `{message}`: 400 — формат, 401 — вход, 403 — CSRF, 404 — заявка недоступна, 409 — конфликт/изменение ставки, 422 — подготовка анкеты не прошла, 502 — источник ставок или сведений недоступен. HTTP-коды ошибок внешних сервисов не трактуются как `found:false`.

Карточка новой заявки дополнительно содержит `bankOfferId` и `bankOfferName`. Если у исторического снимка нет выбранного предложения и единицы ставки, `annualRate` возвращается null и добавляется `rateWarning`; историческая запись в БД не переписывается.
