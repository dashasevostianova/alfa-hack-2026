# Подробная структура проекта

Этот документ объясняет, как устроен фронтенд, за что отвечает каждый файл и где менять код при дальнейшей разработке. Краткий запуск находится в [README.md](README.md), полный контракт для Spring Boot — в [docs/API.md](docs/API.md).

## 1. Общая архитектура

Проект — одностраничное приложение (SPA) на React и TypeScript. Браузер загружает один HTML-документ, а React Router переключает страницы внутри него без полной перезагрузки.

- **React** описывает интерфейс компонентами и обновляет его при изменении состояния.
- **TypeScript** проверяет типы полей, параметров и ответов API во время разработки и сборки.
- **React Router** сопоставляет адрес браузера с компонентом страницы.
- **Vite** запускает сервер разработки, обновляет интерфейс после изменения файлов и собирает production-версию.
- **Vitest** запускает автоматические проверки расчётов, валидации и мокового API.

Приложение разделено на страницы, общие компоненты, API-слой, типы и вспомогательные функции. Страницы работают через единый объект `api`: они не выбирают самостоятельно между браузерной демо-базой и сервером Spring Boot.

## 4. Как запускается приложение

```text
index.html
  → src/main.tsx
    → App.tsx
      → api.me(): восстановление пользователя
      → SessionContext.Provider: общий пользователь
      → BrowserRouter и Routes: выбор страницы
        → LoginPage / RegisterPage
        → Layout → текущая страница кабинета через Outlet
```

### `src/main.tsx`

Импортирует глобальные стили, находит HTML-контейнер `root` и рендерит `App` через `createRoot`. Включает `StrictMode`, который помогает обнаруживать проблемы React во время разработки. Это точка входа, а не место для логики отдельных форм.

### `src/App.tsx`

Хранит текущего пользователя, состояние начальной загрузки, ошибку и номер повторной попытки. При запуске вызывает `api.me()`. До завершения запроса показывает загрузку, при ошибке — возможность повторить запрос.

Передаёт `user` и `setUser` через контекст, объявляет маршруты и слушает событие `session-expired`. При этом событии пользователь сбрасывается, и защищённая оболочка перенаправляет на вход.

### `src/session.tsx`

Объявляет `SessionContext` и хук `useSession()`. Хук позволяет странице или компоненту получить текущего пользователя и обновить его, не передавая эти значения через несколько уровней свойств компонентов.

Контекст живёт в памяти React. Сам по себе он не является хранилищем сессии: после обновления страницы `App` повторно получает пользователя через API.

## 5. Маршруты и доступ

| Адрес | Страница | Условия |
| --- | --- | --- |
| `/login` | `LoginPage.tsx` | Для пользователя без входа. Авторизованный пользователь отправляется на `/data`. |
| `/register` | `RegisterPage.tsx` | Для пользователя без входа. Авторизованный пользователь отправляется на `/data`. |
| `/data` | `DataPage.tsx` | Нужен вход. |
| `/calculator` | `CalculatorPage.tsx` | Нужны вход и сохранённая анкета (`profileComplete`). |
| `/applications` | `ApplicationsPage.tsx` | Нужен вход. Если заявок нет, показывается пустое состояние. |
| `/approved/:id` | `ApprovedPage.tsx` | Нужен вход. `:id` — идентификатор заявки; страница пока не загружает и не проверяет её. |
| Любой неизвестный путь | Перенаправление | На `/data` при наличии пользователя, иначе на `/login`. |

Маршруты кабинета находятся внутри `Layout`. Его `Outlet` — место, куда React Router вставляет соответствующую страницу. При смене вкладки общий заголовок и меню остаются.

Ограничение доступа на фронтенде управляет интерфейсом. Реальный сервер должен отдельно проверять сессию, принадлежность заявки пользователю и разрешение на операцию.

## 6. Страницы: `src/pages/`

### `LoginPage.tsx`

- Хранит введённые логин и пароль, ошибку и состояние отправки.
- Отправляет данные через `api.login()`.
- После успеха обновляет пользователя в контексте и открывает `/data`.
- При ошибке показывает сообщение сервера или мокового API.
- Использует `AuthLayout` и `Field`, содержит ссылку на регистрацию.

### `RegisterPage.tsx`

Проверяет формат логина, требования к паролю и совпадение двух паролей. Затем вызывает `api.loginAvailable()` и `api.register()`. Успешная регистрация по текущему контракту сразу создаёт сессию и переводит на анкету.

Повторный пароль существует только в форме и не отправляется в API. Предварительная проверка логина не заменяет проверку уникальности при регистрации на сервере.

### `DataPage.tsx`

Загружает анкету через `api.getProfile()`. Если анкеты ещё нет, использует `emptyProfile`. Отображает две секции: личные данные и данные бизнеса. Это одна форма и один объект `Profile`.

При сохранении запускает `profileError()`, отправляет анкету через `api.saveProfile()`, сохраняет возвращённые данные и выставляет `profileComplete: true` в контексте. После этого появляется переход к калькулятору и становится доступна соответствующая вкладка.

Изменения полей до нажатия «Сохранить данные» находятся только в состоянии страницы. Автосохранения нет. При ошибке загрузки форма не подставляет пустые значения поверх неизвестных серверных данных — показывает повтор загрузки.

### `CalculatorPage.tsx`

Загружает продукты через `api.getProducts()`. Хранит выбранный продукт, сумму, срок и цель. Проверяет границы выбранного продукта и рассчитывает ориентировочный аннуитетный платёж через `monthlyPayment()`.

При переключении продукта приводит сумму и срок к допустимым границам. Отправляет только `ApplicationDraft` через `api.createApplication()`, после успеха открывает список заявок.

При повторной подаче получает черновик из состояния навигации React Router (`location.state.draft`). В черновике уже могут быть указаны рекомендованная сумма, прежний продукт, срок и цель. Это не изменение старой заявки: отправка создаёт новую.

### `ApplicationsPage.tsx`

Загружает заявки через `api.getApplications()`. Если есть незавершённые, планирует следующий запрос через 3 секунды. Следующий таймер ставится после успешного ответа, поэтому запросы не накладываются друг на друга.

Когда все заявки завершены, автоматическое обновление прекращается. При уходе со страницы таймер очищается. При ошибке показывается кнопка повторной загрузки, а уже полученные заявки остаются на экране.

Каждая карточка содержит цель, продукт, сумму, срок, ставку и `StatusStepper`. После завершения появляется решение с причинами и рекомендациями. Одобрение ведёт на заглушку следующего этапа, возможность пересмотра — на калькулятор с заполненным черновиком.

### `ApprovedPage.tsx`

Пустая область для будущего продолжения оформления после одобрения. Сейчас отображается внутри кабинета, поэтому навигация остаётся доступной. Следующий бизнес-процесс здесь ещё не реализован.

## 7. Общие компоненты: `src/components/`

| Компонент | Что делает | Где используется |
| --- | --- | --- |
| `AuthLayout.tsx` | Рисует логотип, заголовок, подпись, место для формы и отметку учебного проекта. В моковом режиме напоминает о вымышленных данных. | Вход и регистрация. |
| `Field.tsx` | Связывает подпись с `input` через ID, принимает стандартные свойства поля. Для пароля добавляет переключение видимости. | Формы входа, регистрации, анкеты, калькулятора. |
| `Layout.tsx` | Проверяет наличие пользователя, рисует меню и общую область кабинета, выполняет выход через API. Пока анкета не сохранена, показывает недоступную вкладку калькулятора. | Все маршруты кабинета. |
| `StatusStepper.tsx` | Сопоставляет код статуса с одним из четырёх этапов. Выделяет текущий этап красным, предыдущие отмечает завершёнными. | Карточки заявок. |

Общий компонент отвечает за повторяемую часть интерфейса. Логика конкретной страницы — например, отправка заявки — остаётся в странице и API-слое.

## 8. Данные и типы: `src/types.ts`

| Тип | Назначение |
| --- | --- |
| `Credentials` | Логин и пароль для входа/регистрации. |
| `User` | ID, логин и признак полной анкеты. |
| `Profile` | Личные и бизнес-данные в одном объекте. Состав пока временный. |
| `LoanProduct` | Продукт, описание, ставка, минимальные и максимальные сумма/срок. |
| `Purpose` | Одна из допустимых целей; выводится из массива `purposes`. |
| `ApplicationDraft` | Параметры новой заявки: сумма, месяцы, цель, ID продукта. |
| `ApplicationStatus` | `SUBMITTED`, `VERIFICATION`, `REVIEW`, `COMPLETED`. |
| `Decision` | Итог, пояснение, причины, рекомендации и необязательная рекомендуемая сумма. |
| `LoanApplication` | Черновик плюс ID, дата, зафиксированные название продукта и ставка, статус и решение. |

Типы описывают ожидаемую структуру данных, но не выполняют проверку JSON во время исполнения. Spring Boot должен возвращать согласованный формат. Если контракт меняется, нужно согласованно обновить типы, адаптер, моки и затронутые страницы.

## 9. Работа с API: `src/api/`

### `index.ts`: единая точка доступа

Экспортирует `api` и признак `useMocks`. Моки включены, если `VITE_USE_MOCKS` не равен строке `false`. Поэтому приложение запускается без env-файла и без бэкенда.

В реальном режиме общий `request<T>()`:

1. Формирует адрес из базового URL и пути.
2. Добавляет JSON-заголовки, если есть тело.
3. Перед изменяющим запросом получает CSRF-токен через `/auth/csrf`.
4. Отправляет запрос с `credentials: include` для cookie-сессии.
5. Обрабатывает 204 без тела, JSON-ответы и сообщения об ошибках.
6. Для 401 от `/auth/me` возвращает `null`; для неверного входа показывает ошибку формы; для остальных обработанных 401 инициирует `session-expired`.

HTTP-методы и пути собраны в `httpApi`, а не распределены по страницам.

| Метод объекта `api` | HTTP-запрос в серверном режиме |
| --- | --- |
| `me()` | `GET /api/auth/me` |
| `login(credentials)` | `POST /api/auth/login` |
| `register(credentials)` | `POST /api/auth/register` |
| `logout()` | `POST /api/auth/logout` |
| `loginAvailable(login)` | `GET /api/auth/login-availability?login=...` |
| `getProfile()` | `GET /api/profile` |
| `saveProfile(profile)` | `POST /api/profile` |
| `getProducts()` | `GET /api/loans/products` |
| `getApplications()` | `GET /api/applications` |
| `createApplication(draft)` | `POST /api/applications` |

`GET /api/auth/csrf` вызывается внутренним HTTP-помощником. Форматы тел, ответов и кодов ошибок приведены в [docs/API.md](docs/API.md).

### `mock.ts`: замена сервера для демонстрации

Реализует тот же интерфейс `Api`, но хранит данные в браузере:

| Хранилище | Ключ | Содержимое |
| --- | --- | --- |
| `localStorage` | `alpha-hackathon-demo-v1` | Список аккаунтов: пользователь, демо-хеш пароля, анкета, заявки. |
| `sessionStorage` | `alpha-hackathon-session-v1` | ID пользователя активной демо-сессии. |

`readDb()` и `writeDb()` читают и записывают демо-базу. `current()` выбирает текущий аккаунт. Каталог продуктов находится в массиве `products`.

`progressApplication()` вычисляет этап по времени создания: до 5 секунд — отправлено, до 10 — проверка, до 15 — рассмотрение, затем — завершено. `demoDecision()` выбирает итог по демонстрационным границам суммы. При чтении списка вычисленные статусы сохраняются обратно в демо-базу.

Это имитация сервера для проверки UI, а не система кредитного скоринга или защищённая авторизация. В серверном режиме статусы и решения приходят из Spring Boot, и эти функции не определяют результат заявки.

## 10. Вспомогательная логика и стили

### `src/lib.ts`

- `money()` форматирует рубли для отображения.
- `monthlyPayment()` считает аннуитетный платёж и отдельно обрабатывает нулевую ставку.
- `loginPattern` задаёт допустимый формат логина.
- `passwordValid()` проверяет минимальную длину и оба регистра латинских букв.
- `profileError()` возвращает первое найденное нарушение в анкете либо `null`.
- `errorMessage()` превращает неизвестную ошибку в текст для интерфейса.

Проверка реквизитов здесь базовая. Например, длина ИНН проверяется, а контрольная сумма и наличие компании в реестре — нет.

### `src/styles.css`

Все стили пока находятся в одном файле. Основные группы:

- `:root` — шрифт, базовые цвета, CSS-переменные `--accent`, `--muted`, `--field`.
- `.auth-*` — вход и регистрация.
- `.field`, `.button`, `.error`, `.hint` — общие элементы форм.
- `.header`, `.surface`, `.content`, `.card` — оболочка и блоки кабинета.
- `.calculator`, `.product-*`, `.calculation-summary` — калькулятор.
- `.application-*`, `.stepper`, `.decision-*` — заявки и решения.
- Медиа-запросы на 950 и 650 px — адаптация колонок, отступов и навигации.

Manrope подключается через Google Fonts; если он недоступен, используется Arial. Отдельной папки изображений сейчас нет: логотип и элементы интерфейса выполнены текстом и CSS.

## 11. Пример прохождения данных

Сохранение анкеты:

```text
Поля DataPage
  → локальное состояние Profile
  → profileError()
  → api.saveProfile(profile)
    → mockApi: запись в localStorage
    или
    → httpApi: POST /api/profile → Spring Boot → база данных
  → сохранённый Profile в ответе
  → обновление формы и user.profileComplete
  → доступный калькулятор
```

Подача и рассмотрение заявки:

```text
CalculatorPage
  → ApplicationDraft
  → api.createApplication()
  → переход на /applications
  → api.getApplications()
  → карточки + StatusStepper
  → периодическое обновление незавершённых заявок
  → Decision
    → APPROVED: следующий этап
    → REVISION: новый черновик в калькуляторе
    → REJECTED: причины и рекомендации
```

Платёж в калькуляторе считается локально для предварительного отображения. Реальный сервер независимо проверяет параметры и берёт ставку из своего каталога.

## 13. Запуск, проверки и сборка

В терминале PyCharm из корня проекта:

```powershell
npm.cmd install
npm.cmd run dev
```

Приложение доступно по адресу `http://127.0.0.1:5173`. Vite настроен на `strictPort: true`: если порт занят, команда завершится ошибкой вместо перехода на другой порт.

```powershell
npm.cmd test
npm.cmd run build
npm.cmd run preview
```

| Команда | Результат |
| --- | --- |
| `dev` | Сервер разработки с обновлением интерфейса после изменения исходников. |
| `test` | Запуск Vitest. |
| `build` | Проверка TypeScript и сборка статических файлов в `dist/`. |
| `preview` | Локальный просмотр уже собранной версии; адрес показывает терминал. |

`lib.test.ts` проверяет расчёт платежа, пароль и валидацию анкеты. `api/mock.test.ts` проверяет вход, дубликат логина, выход, изоляцию аккаунтов, запрет подачи без анкеты, параметры заявки, этапы и варианты решения. В тестах используются отдельные хранилища в памяти, а не данные браузера пользователя. Автоматические UI-тесты в репозитории пока не добавлены.

## 14. Переход с моков на Spring Boot

Создайте `.env.local` из примера и задайте:

```dotenv
VITE_USE_MOCKS=false
VITE_API_BASE_URL=/api
```

После перезапуска Vite запросы `/api` будут перенаправляться локальному Spring Boot через dev-прокси. Сами страницы менять не требуется, если сервер соблюдает контракт.

Демо-аккаунты и анкеты не переносятся автоматически на сервер. В реальном режиме используются серверные пользователи, база данных и cookie-сессия.

Для production нужен отдельный reverse proxy или сервер раздачи: dev-прокси Vite не входит в `dist/`. Маршруты приложения должны отдавать `index.html` через SPA fallback, а `/api/*` — обрабатываться Spring Boot. Настройка production-развёртывания в этом репозитории пока не реализована.
