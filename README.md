# Кредитный кабинет: общий запуск

Ветка `dev-2`: React → Java API → PostgreSQL, сервис подготовки данных компании и парсер ставок.

## Windows: запуск одной командой

Нужен Docker Desktop в режиме Linux containers. Отдельную Linux-систему устанавливать не требуется: Docker Desktop использует WSL 2. Запустите Docker Desktop и дождитесь готовности движка.

В PowerShell из корня репозитория:

```powershell
docker compose up --build -d --wait
```

Откройте **http://127.0.0.1:8088**. Первый запуск скачивает образы, Java/npm/Python-зависимости и Chromium парсера, поэтому занимает несколько минут. Флаг --wait дожидается готовности API через nginx; при ошибке проверьте логи сервисов.

Не запускайте старый `Docker/docker-compose.yml` для общего сценария: новый файл находится в корне и называется `compose.yaml`.

```powershell
docker compose ps
docker compose logs --tail=100 backend
docker compose logs --tail=100 parser
docker compose logs --tail=100 formation
docker compose down
```

`down` останавливает сервисы, сохраняя том базы. Повторный запуск: `docker compose up -d`. Не используйте `down -v`, если данные нужны.

## Настройки

Настройки для локального запуска уже заданы в Compose. При необходимости скопируйте `.env.example` в `.env` и измените порт или реквизиты новой базы перед её первым запуском:

```powershell
Copy-Item .env.example .env
```

Фронтенд опубликован только на loopback Windows. БД, Java, formation и parser доступны друг другу по внутренней Docker-сети и не публикуют порты на хосте.

Compose использует отдельный том проекта `alpha-credit`. Данные из старого `Docker/docker-compose.yml` автоматически не переносятся и не удаляются. Изменение POSTGRES_PASSWORD в env не меняет пароль уже созданной БД.

## Пользовательский путь

1. Зарегистрируйте тестовый аккаунт. Вход и регистрация выглядят как раньше, но теперь работают через Java и PostgreSQL, с cookie-сессией и CSRF.
2. Заполните ФИО, телефон, почту и паспорт. Дата рождения и гражданство добавлены, поскольку они обязательны в существующей таблице `person`; фиктивные значения не подставляются.
3. Введите компанию, сферу, ИНН и месячную выручку. Пример ИНН из предоставленного CSV: `4217064462`.
4. Formation проверяет ИНН и рассчитывает показатели существующими функциями. Если ИНН отсутствует, форма открывает ручное заполнение реквизитов и финансов. Ошибка источника не трактуется как отсутствие компании.
5. Сохраните анкету. Java повторно готовит данные через formation и сохраняет полный черновик в БД.
6. Выберите сумму, срок кредита, цель и наличие залога. Форма бизнеса и возраст определяются из сохранённых реквизитов. На сайте банка фильтр относится к **возрасту бизнеса**, а не к сроку кредита: ООО — до/более 9 полных месяцев, ИП — до/более 3 полных месяцев. Это уточнение согласовано вместо исходного правила документа.
7. Дождитесь списка предложений и выберите конкретное предложение банка. Новый endpoint парсера загружает только нужное сочетание формы, возраста и залога; запрос может занять до 3 минут. Java кэширует результат на 5 минут по этим условиям. У каждого предложения сохраняются имя, ID, ставка и единица измерения. «Альфа-Селлер Кредит» публикует месячную переплату, которая не считается годовой ставкой. Предложения без сопоставимой годовой ставки показаны для справки, расчёт и подача по ним недоступны. Ошибка источника не заменяется статичной ставкой.
8. При отправке Java проверяет ID выбранного предложения и его годовую ставку ещё раз и вызывает существующий `ApplicationService.submit()`. Если ставка изменилась, нужно обновить расчёт. Заявка, человек, компания и финансы сохраняются транзакционно.
9. После отправки показывается прежняя анимация подготовки, затем сохранённый отчёт. Модель ещё не подключена: новые заявки остаются отправленными, искусственные решения об одобрении не создаются. Существующие решения из БД отображаются.

Пределы суммы и срока берутся из `product`. В пустую БД добавляется один явно обозначенный учебный продукт с лимитами из прежнего демо; его ставка NULL и не используется в расчёте. Актуальная ставка берётся исключительно из parser. Лимиты учебного каталога не являются банковским предложением.

## Архитектура

```text
Браузер :8088 → nginx → Java :8080 → PostgreSQL :5432
                                ├→ formation :8081 → companies_small.csv
                                └→ parser :8000 → калькулятор банка
```

- `frontend/` — страницы, формы, расчёт отображаемого платежа и клиент API.
- `backend/hack/` — существующие Java-сущности и сервис записи; дополнительные адаптеры в пакете `integration`.
- `backend/formation/server.py` — исходные формулы и проверки, не изменён.
- `backend/formation/lookup_server.py` — HTTP-оболочка только для чтения/подготовки. Не создаёт пользователей и заявки, не подключается к БД.
- `backend/formation/data/companies_small.csv` — предоставленная таблица; монтируется read-only.
- `parser/` — предоставленный FastAPI/Playwright-парсер с добавленным GET `/offers`. Существующие GET `/` и функция `get_credit_rate` сохранены; новый запрос выбирает сначала форму регистрации, затем соответствующий возраст бизнеса и залог. `offers.py` извлекает видимые карточки только из блока калькулятора.
- `Docker/init/01_schema.sql` — исходная схема.
- `Docker/init/03_integration.sql` — добавочная таблица `integration_profile` для анкеты до выбора продукта и начальный каталог только для пустой БД. Существующие таблицы не удаляются и не переименовываются.
- `compose.yaml` — общий запуск всех сервисов. Сервис `migrate` повторно безопасно применяет добавочный SQL и к существующему тому.

В `finances.account_statements` хранится JSON-снимок `integration_snapshot_v1`: анкета, источник данных, показатели, список предложений, выбранный `bankOffer`, ставка, время получения и залог на момент подачи. Существующие числовые столбцы finances заполняются отдельно через Java-сервис. Это позволяет сохранять условия прошлой заявки после редактирования анкеты.

Подробный актуальный контракт: [docs/INTEGRATION.md](docs/INTEGRATION.md). Структура всего проекта: [struktura.md](struktura.md). Готовность и отложенные задачи: [OSTALOS.md](OSTALOS.md).

## Разработка вне Docker

Полный запуск выше не требует локальных Java, Python или Node.js. Для отдельной разработки фронтенда нужны Node.js 22.12+ и Java API на localhost:8080:

```powershell
cd frontend
npm.cmd ci
npm.cmd run dev
```

Vite проксирует весь `/api` на Java, включая запросы к formation. Для изолированного старого браузерного демо можно задать `VITE_USE_MOCKS=true` в `frontend/.env.local`; это отдельный режим, его аккаунты и заявки не мигрируют в PostgreSQL. Docker-сборка явно включает реальный API.

## Проверки

```powershell
cd frontend
npm.cmd test
npm.cmd run build
cd ../backend/hack
.\mvnw.cmd --batch-mode --no-transfer-progress test -Dtest=ApplicationServiceTests,ExternalServicesTests
```

Python-проверки (с установленным `backend/formation/requirements.txt`), из корня:

```powershell
python -m unittest discover -s backend/formation -v
```

Один старый DB-тест требует специального `FORMATION_TEST_DB=1` и работающей БД; обычные unit-тесты используют синтетические данные.

Сквозная проверка запущенного Compose (только локальная тестовая БД):

```powershell
python scripts/check_integration.py
```

Она создаёт синтетические аккаунты и заявки и оставляет их в локальной БД. Проверяет 8 сочетаний возраста/формы/залога, отдельные сроки кредита 9/10 месяцев, выбор предложения, отказ при неверной ставке/ID/сумме, неподдерживаемые единицы ставок, повторный вход, неизменность снимков и изоляцию аккаунтов. Нужны доступный сайт банка и Python 3.9+; внешние Python-пакеты этому скрипту не требуются. Другой локальный адрес можно задать через `APP_URL`.

Тесты парсера в уже запущенном Compose:

```powershell
docker compose exec -T parser python -m unittest test_offers -v
```

Java-тесты без локальной Java, из корня:

```powershell
docker build --target build -t alpha-credit-java-tests backend/hack
docker run --rm alpha-credit-java-tests ./mvnw --batch-mode --no-transfer-progress test "-Dtest=ApplicationServiceTests,ExternalServicesTests"
```

## Ограничения текущего этапа

- Реальный скоринг не подключён; состояние заявки меняется только по данным БД, а не по демонстрационному таймеру.
- Сессии Java пока в памяти: перезапуск Java требует повторного входа. Пользователи, анкеты и заявки сохраняются в PostgreSQL.
- Парсер зависит от доступности и разметки сайта банка. Изменения внешнего сайта могут потребовать доработки предоставленного парсера.
- Парсер фильтрует предложения по форме, возрасту бизнеса и залогу. Сумма и срок в кабинете проверяются по учебному каталогу `product`; они не переносятся в поля внешнего калькулятора. Расчёт аннуитетный и предварительный, включая выбор кредитной линии/овердрафта: их фактические графики и доступные лимиты нужно уточнять по ссылке на продукт.
- Старые заявки без названия предложения и единицы ставки сохраняются, но их прежняя ставка не отображается как подтверждённая годовая; UI предлагает уточнить условия новым расчётом.
- В исходной схеме суммы — PostgreSQL INTEGER. Переполнение проверяется formation; миграция на BIGINT/NUMERIC не выполняется.
- Проект предназначен для локального хакатона. Production-настройки HTTPS, ограничения частоты запросов, аудит и развёртывание здесь не реализованы.
